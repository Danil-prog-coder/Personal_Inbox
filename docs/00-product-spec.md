# Personal Inbox — ТЗ продукта

> Статус: зафиксировано. Открытых вопросов нет.
> Если при работе возник вопрос, ответа на который нет в `docs/` — см. раздел 9.

---

## 1. Что это

Одна лента вместо десяти вкладок. Сообщения из Gmail и Telegram собираются в одном
месте. Каждое проходит через языковую модель и получает четыре характеристики:

1. **Уровень важности** — один из четырёх фиксированных (CRITICAL / HIGH / NORMAL / LOW)
2. **Категорию** — свободная строка от модели («Юридическое», «Финансы», «Найм»…)
3. **Срок** — свободная строка от модели («Сегодня, 18:00», «Пятница», пусто)
4. **Признаки** — «требует ответа» (reply) и «требует действия» (action)

Плюс краткое содержание (summary) в 1–2 предложения.

Пользователь описывает свои критерии важности **свободным текстом**, а не правилами.
Он может исправить уровень важности вручную — исправление уходит в модель как обратная
связь при следующих оценках.

**Это pet-проект, не продакшн.** Решения принимаются в пользу простоты:
никакого Kubernetes, микросервисов, брокеров сообщений, multi-tenancy.
Один процесс приложения, один пользователь на инсталляцию; хранилища —
Postgres и Redis, оба поднимаются вместе со стеком.

## 2. Технологический стек — зафиксировано

| Слой | Решение | Почему |
| --- | --- | --- |
| Фронтенд | **React 18 + TypeScript + Vite** | Референс написан на React 18, стили переносятся один-в-один |
| Стили | **Обычный CSS + CSS-переменные** из `docs/reference/design-tokens.css` | Референс — инлайновый CSS на переменных. Tailwind/CSS-in-JS запрещены: они ломают точный перенос |
| Состояние | Локальный `useState`/`useReducer` + `fetch` | Redux/Zustand/React Query не нужны на таком объёме |
| Роутинг | `react-router-dom` | 4 вкладки + два уровня ленты |
| Бэкенд | **Go 1.25+, стандартная библиотека** `net/http` | Один статический бинарник, никакого рантайма на машине. Маршрутизация с методом и путём (`GET /api/messages/{id}`) есть в stdlib с 1.22 — веб-фреймворк не нужен |
| БД | **PostgreSQL 16** через `database/sql` + `pgx` | Настоящий сервер БД, а не файл: типы `timestamptz` и `boolean` вместо строк, Unicode-`lower()` вместо своей функции. Драйвер на чистом Go — сборка без cgo |
| Кэш | **Redis 7** через `go-redis` | Сводка и счётчики источников кэшируются на 45 секунд; плюс одноразовый state OAuth. Сессий нет — входа в приложение тоже (решение №50) |
| Доступ к данным | **Обычный SQL** в `internal/postgres` | ORM на четыре таблицы не окупается; запросы видно целиком |
| Миграции | Свои `.sql` в `internal/postgres/migrations`, встроены через `embed` | Аналог Alembic на 60 строк: файлы по порядку плюс таблица `schema_migrations` |
| Фоновые задачи | **Горутина с `time.Ticker`** в том же процессе | Отдельный воркер и брокер — избыточны |
| Очередь оценки | Одна горутина-воркер и очередь в памяти | Одного потока хватает; сообщения не теряются при переоценке всей ленты |
| Модель | **OpenAI API** через адаптер `internal/openai` | Смена провайдера = один файл. Обычный HTTP-запрос вместо SDK. Модель по умолчанию — `gpt-4o-mini` |
| Gmail | Google OAuth 2.0 + Gmail REST API поверх `net/http` | Шесть запросов — SDK не нужен |
| Telegram | **Клиентский API (MTProto)** через `gotd/td` | Бот не видит личную переписку — см. п. 5.2 |
| Тесты | `go test` (бэк), `vitest` (фронт) | |
| Запуск | `docker compose up --build` — весь стек (postgres + redis + бэкенд + nginx) одной командой; `make run` и `make front` — для разработки без контейнеров | |

Зависимостей у бэкенда две: драйверы Postgres и Redis. Веб-фреймворк, ORM,
логгер, планировщик и SDK провайдеров сознательно не подключаются — всё это
закрывается стандартной библиотекой, а лишняя зависимость на pet-проекте дороже
двадцати строк своего кода.

Что **не** делаем, даже если кажется правильным: CI/CD, мониторинг, Sentry,
rate-limiting, аудит-логи, шифрование БД, multi-workspace.

## 3. Язык и локализация

Интерфейс **только русский**. Строки пишутся прямо в коде, i18n-библиотека не подключается.
Тексты кнопок, заголовков и пустых состояний — брать дословно из референса, где они есть
(`docs/02-screens.md` содержит их полный список).

Модель отвечает по-русски: категории, срок и summary — на русском, независимо от языка
исходного сообщения.

## 4. Носители и темы

Один адаптивный интерфейс, **не два разных дизайна**:

| Носитель | Ширина | Навигация | Детали сообщения |
| --- | --- | --- | --- |
| Телефон | `< 900px` | Нижний таб-бар, 4 вкладки | Лист снизу, почти во весь экран |
| Десктоп | `>= 900px` | Левая боковая панель 252px | Панель справа |

Обе темы (тёмная и светлая) обязательны и переключаются в настройках.
Тема применяется атрибутом `data-theme="dark" | "light"` на корневом элементе.
Ни один цвет не задаётся мимо переменных из `design-tokens.css`.

## 5. Источники

### 5.1 Gmail
- Подключение через Google OAuth 2.0, scope `gmail.readonly`.
- Синхронизация: фоновая горутина, **раз в 5 минут**, инкрементально по `historyId`.
- При первом подключении импортируются письма **за последние 30 дней**, максимум 200 штук.
- Токен истёк / отозван → источник переходит в `REAUTH_REQUIRED`, ранее полученные
  сообщения остаются в ленте.

### 5.2 Telegram
- **Клиентский API (MTProto)**, тот же, на котором работают официальные приложения.
  Bot API не подходит принципиально: бот видит только чаты, куда его добавили,
  и личную переписку не отдаёт вовсе — это ограничение платформы (решение №52).
- Ключи `api_id` и `api_hash` берутся на my.telegram.org и задаются через
  окружение. Без них подключение недоступно, и приложение честно об этом говорит.
- Подключение в два-три шага: номер телефона → код из Telegram → облачный пароль,
  если включена двухфакторная защита.
- Сессия хранится в `connection.credentials`. Она даёт **полный доступ к аккаунту**,
  а не только чтение: обращаться с ней нужно как с паролем. Отключение источника
  стирает её.
- Синхронизация: раз в 5 минут забираются верхние 40 диалогов, из каждого — до 30
  последних сообщений; лишнее отсеивает дедупликация по внешнему id. Первое
  подключение импортирует месяц, максимум 200 сообщений (решение №16).
- Свои отправленные сообщения, служебные события и медиа без подписи в ленту
  не попадают.

### 5.3 Источники из планов развития
VK и GitHub показываются в экране выбора сервиса **неактивными, с пометкой
«Скоро»**. Это решённый вопрос: показываем, а не скрываем. Всего в списке
четыре строки (решение №51).

## 6. Обработка сообщения моделью

### 6.1 Жизненный цикл
```
получено из источника
  → status = PROCESSING   (в ленте видны отправитель, тема, текст; на месте
                           оценки — индикатор «Определяем важность…»)
  → вызов модели
  → status = DONE         (появились level, cat, deadline, reply, action, summary)
```
Если вызов модели упал — повтор до 3 раз с задержками 2с / 8с / 30с.
После трёх неудач: `status = DONE`, `level = NORMAL`, `cat = ''`, `summary = ''`,
и на карточке маленькая пометка «Оценка недоступна». Сообщение **никогда** не пропадает
из ленты из-за ошибки модели.

### 6.2 Что уходит в модель
Один запрос на сообщение. В промпт кладём: критерии пользователя, отправителя, тему,
текст (обрезанный до 4000 символов), источник, и последние **до 20 ручных исправлений**
пользователя в формате «тема → уровень, который поставил пользователь».

Ответ — строгий JSON (structured output):
```json
{
  "level": "CRITICAL|HIGH|NORMAL|LOW",
  "category": "строка на русском, 1–2 слова",
  "deadline": "строка на русском или пустая",
  "needs_reply": true,
  "needs_action": true,
  "summary": "1–2 предложения на русском"
}
```
Всё, что не соответствует схеме, считается ошибкой вызова (см. 6.1).

### 6.3 Хранение
Полный текст сообщения **хранится в БД**. Это обязательно: без него не работают поиск,
экран деталей и фоновая переоценка при смене критериев.

### 6.4 Смена критериев
Сохранение новых критериев ставит **все** сообщения в очередь на переоценку
(`status = PROCESSING`), она идёт фоном, партиями по 10. Пользователь предупреждается
об этом плашкой перед сохранением. Ручные исправления уровня при переоценке
**не затираются**: если у сообщения есть `level_override`, показывается он.

## 7. Структура ленты

Два уровня. Сквозной вкладки «Все источники» нет.

- **Уровень 1** — карточки подключённых источников. Отключённые не показываются.
- **Уровень 2** — сообщения одного источника. Поиск и фильтры действуют здесь.

Подробно — `docs/02-screens.md`.

---

## 8. Не входит в MVP

Не проектировать и не кодить:

- Ответ на сообщение внутри приложения — только переход в оригинальный сервис
- Push-уведомления на устройство
- Источники, кроме Gmail и Telegram
- Пользовательская настройка уровней важности (их ровно 4, они фиксированы)
- Фильтр по произвольному диапазону дат (календарь)
- История изменений сообщений
- Пагинация и бесконечный скролл; состояния ошибки сети сверх п. 6.1
- Multi-workspace, командные функции, роли
- Вложения: показываем только имя файла, скачивание не делаем
- Тред-вью писем: одно письмо = одна карточка
