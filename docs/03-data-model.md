> Зафиксировано. Имена полей и значения enum менять нельзя без правки этого файла.

## 1. Перечисления

```go
Levels      = "CRITICAL" | "HIGH" | "NORMAL" | "LOW"     // ровно 4, фиксированы
SourceKinds = "gmail" | "telegram"                       // в MVP только эти
ConnStates  = "off" | "active" | "reauth"                // три состояния подключения
MsgStatuses = "PROCESSING" | "DONE"                      // статус оценки моделью
```

Списки объявлены в `backend/internal/postgres/models.go` и проверяются функцией
`store.Contains`: значение вне списка — это 422, а не запись мусора в базу.

`level` в БД хранится строкой из четырёх значений выше — не числом, не индексом.
На фронте `LEVEL_ORDER = ["CRITICAL", "HIGH", "NORMAL", "LOW"]` — порядок
и для сортировки, и для полос распределения, и для переключателя в деталях.

| Поле | Тип | Заметки |

`UNIQUE (connection_id, external_id)` — защита от дублей при повторной синхронизации.
Индексы: `(connection_id, received_at DESC)`, `(connection_id, is_read)`.

**Эффективный уровень** = `level_override` → `level` → `"NORMAL"`, первое непустое.
Везде — в ленте, фильтрах, сводке, полосах — используется он. Отдельной колонки
под него нет: в Go это метод `Message.EffectiveLevel()`, в SQL — тот же расчёт
через `COALESCE(NULLIF(...))` (`store.effectiveLevelSQL`), чтобы фильтр по уровню
считал так же, как показывает интерфейс.

## 3. Категория и срок — свободные строки

Оба поля модель возвращает текстом, фиксированного справочника нет.
Причина: набор категорий у каждого пользователя свой, а срок в реальных сообщениях
формулируется как «до конца недели», «через 5 дней» — приводить это к дате
без потери смысла нельзя.

Следствия, которые обязательно учесть:
- Фильтра по категории нет (в референсе его тоже нет)
- `deadline_text` **не сортируется и не сравнивается** — только показывается
- Категория выводится как есть; если пустая — чип не рендерится вообще
- Модель просят вернуть категорию в 1–2 слова, но полагаться на это нельзя:
  чип обрезается по `max-width` с многоточием

## 4. Фильтр «Период»

Считается по `received_at` относительно текущего момента:

| Вариант | Условие |
| --- | --- |
| `all` — Всё время | без ограничения |
| `today` — Сегодня | с 00:00 сегодняшнего дня по локальному времени пользователя |
| `week` — Неделя | последние 7×24 часа |
| `month` — Месяц | последние 30×24 часа |

`today` считается по локальному времени пользователя, поэтому фронт передаёт
в `/api/messages` параметр `tz_offset` — смещение часового пояса в минутах
(`-new Date().getTimezoneOffset()`). Без него «Сегодня» считалось бы по UTC.

В референсе этот фильтр объявлен, но в функции сопоставления не применён —
это баг прототипа, а не решение. **В продукте фильтр обязан работать.**

## 5. Периоды сводки

`24ч` · `Неделя` · `Месяц` — три сегмента.

Это правка референса: там третий сегмент назывался `Период` и подписывался
«Произвольный диапазон», что противоречит решению «календаря в MVP нет».
Заменено на `Месяц`, подпись — `За последние 30 дней`. См. решение №9 в `04-decisions.md`.

Сводка считается по `received_at` в выбранном окне, **по всем источникам сразу**.

## 6. HTTP API

Сессий в Redis нет: входа в приложение не существует. Остался одноразовый
`oauth:<user_id>` на 10 минут — state подтверждения Google, читается один раз
и сразу удаляется.

Кэш — ключи `cache:<user_id>:<имя>` со сроком 45 секунд: `sources` и
`summary:<период>`. Сбрасывается на любой записи, которая меняет ленту.

Все ответы — JSON. Аутентификации нет: сервер сам берёт единственного
пользователя установки (решение №50). Приложение слушает локально и не
предназначено для выставления наружу.

Ошибка возвращается как `{"detail": "текст по-русски"}` — этот формат читает
`frontend/src/lib/api.ts`. Даты в ответах — ISO без зоны и без суффикса
(`2026-09-02T09:41:00`), всегда UTC: «Z» дописывает фронт (`lib/format.ts`).

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/me` | профиль: критерии, тема, плотность |
| `PATCH` | `/api/me` | смена темы, плотности, критериев |
| `GET` | `/api/connections` | список с состояниями и `last_sync_at` |
| `POST` | `/api/connections/gmail/start` | вернуть URL авторизации Google |
| `GET` | `/api/connections/gmail/callback` | приём кода OAuth |
| `POST` | `/api/connections/telegram` | `{bot_token}`, проверка через `getMe` |
| `DELETE` | `/api/connections/{kind}` | отключить |
| `GET` | `/api/sources` | карточки уровня 1: счётчики, распределение, самое срочное |
| `GET` | `/api/messages` | `?source=&level=&status=&reply=&action=&period=&q=&tz_offset=` |
| `GET` | `/api/messages/{id}` | детали |
| `POST` | `/api/messages/{id}/read` | пометить прочитанным |
| `POST` | `/api/messages/{id}/level` | `{level}` — ручное исправление |
| `GET` | `/api/summary` | `?period=24h|week|month` |

Значения фильтров в `/api/messages`: `level` — `all` или один из четырёх уровней;
`status` — `all` \| `unread` \| `read` \| `done`; `reply` и `action` — `all` \| `yes` \| `no`;
`period` — `all` \| `today` \| `week` \| `month`.

Ответ `/api/messages` — объект `{items, total, unread}`: счётчики нужны подзаголовку
«N сообщений · M непрочитанных», который пересчитывается по текущим фильтрам.
Ответ `PATCH /api/me` — `{user, reanalyze_queued}`: второе поле говорит фронту,
сколько сообщений ушло на переоценку после смены критериев.

### 6.1 Как новые сообщения попадают на фронт

**Server-Sent Events**, `GET /api/stream`. Не WebSocket: поток односторонний,
SSE переподключается сам и работает через обычный HTTP.

События: `message.created` (карточка появляется в статусе `PROCESSING`) и
`message.analyzed` (карточка достраивается). Формат payload — та же схема,
что у `GET /api/messages/{id}`.

Если SSE недоступен — фронт откатывается на опрос `/api/messages` раз в 30 секунд.

## 7. Демо-данные

19 сообщений из референса (11 Gmail, 8 Telegram) переносятся в
`backend/internal/services/seed/seed.go` **дословно** и заливаются командой `make seed`.

Набор специально разнородный, и это его смысл: длинная тема, сообщение без срока,
критичное сообщение без необходимости ответа, групповой чат вместо адреса, бот.
На нём проверяются крайние случаи вёрстки. **Не заменять на «lorem ipsum»
и не сокращать набор.**

Три сообщения из очереди живой демонстрации (`_queue` в референсе) переносятся тоже —
на них тестируется появление новых сообщений в реальном времени.
