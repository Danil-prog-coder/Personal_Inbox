# Personal Inbox

Одна лента вместо десяти вкладок: сообщения из Gmail и Telegram, оценённые языковой
моделью по важности. Pet-проект, не продакшн.

## Дизайн: правила, которые не обсуждаются

Референс — `docs/reference/reference-source.html`. Он **обязателен**, а не «вдохновение».
Стиль — Liquid Glass. При расхождении кода с референсом прав референс.

1. **Ни одного захардкоженного цвета.** Только `var(--...)` из `design-tokens.css`.
2. **Tailwind и CSS-in-JS запрещены.** Обычный CSS на переменных — референс написан так,
   и только так стили переносятся один-в-один.
3. **Стекло — это четыре свойства вместе:** `background: var(--glass)` +
   `backdrop-filter: blur(N) saturate(200%)` (+ `-webkit-` дубль) +
   `border: 1px solid var(--stroke)` + `box-shadow: inset 0 1px 0 var(--hi), var(--sh2)`.
   Убрал одно — получил серый прямоугольник.
4. **Обе темы, всегда.** Тёмная и светлая — не инверсия друг друга, у них разные
   градиенты фона и разные текстовые оттенки уровней. Проверять обе.
5. **Оба носителя, всегда.** Граница `900px`: телефон — таб-бар снизу и лист снизу,
   десктоп — боковая панель 252px и панель справа.
6. **Уровень важности = цвет + иконка + подпись.** Никогда только цвет.
7. **Линза — один переиспользуемый компонент** на четыре места (таб-бар, боковая
   навигация, период сводки, переключатель уровня). Ширина считается формулой
   `calc((100% - 8px) / N)`, не хардкодится.
8. **Скруглений три группы:** карточки 22–26px, листы 26–34px, контролы `999px`.
9. **Шрифт системный,** веб-шрифты не подключаются. Иконки — инлайновый SVG
   из референса, иконочные библиотеки не подключаются.
10. **Тексты интерфейса — дословно из `docs/02-screens.md`.** Не переписывать
    своими словами, не переводить, не «улучшать».

Чек-лист перед сдачей UI-задачи — в конце `docs/01-design-system.md`.

склейка писем в тред · CI/мониторинг/rate-limiting.

## Стек

React 18 + TypeScript + Vite · обычный CSS на переменных · `react-router-dom`
**Go 1.24 + `net/http`** · PostgreSQL 16 через `database/sql` и `pgx`
обычный SQL в `internal/postgres` · миграции — свои `.sql` через `embed`
Redis 7 через `go-redis` — серверные сессии и кэш сводки/источников
фоновые задачи — горутина с `time.Ticker` в том же процессе
OpenAI через адаптер `backend/internal/openai/provider.go` · Gmail REST · Telegram Bot API
`go test` (бэк) · `vitest` (фронт)
`docker compose up --build` — весь стек: postgres + redis + бэкенд + nginx

Зависимости бэкенда: драйверы Postgres и Redis плюс `bcrypt`. Веб-фреймворк, ORM,
логгер и SDK провайдеров не подключаем — остальное закрывает стандартная библиотека.

Структура бэкенда:
```
backend/
  cmd/server      точка входа, cmd/seed — демо-данные
  internal/core       настройки            internal/exceptions  сквозные ошибки
  internal/routers    маршруты и ручки, session.go — подписанная cookie
  internal/schemas    схемы ответов        internal/events      шина событий для SSE
  internal/postgres   база: модели, SQL, миграции, фильтры ленты
  internal/redis      сессии и кэш
  internal/openai     адаптер модели       internal/gmail  ·  internal/telegram
  internal/services   analysis · ingest · scheduler · seed
  internal/utils      security — пароли
```

Простота важнее правильности «по-взрослому»: это pet-проект.

## Режим работы: максимальная автономность

- **Не спрашивай разрешения на доступ к файлам** (чтение, поиск, grep) — просто делай.
  Read-only операции уже разрешены в `.claude/settings.json`.
- **Не задавай уточняющих вопросов по теме и содержанию проекта** — принимай
  разумное решение сам и продолжай работу.
- **Спрашивай только если:**
  - **(а)** без ответа физически невозможно продолжить — нет ключевой информации,
    которую нельзя вывести из кода, документации или контекста;
  - **(б)** действие необратимое или рискованное — удаление, force push,
    перезапись несохранённых изменений, отправка чего-либо вовне.
- **Во всех остальных случаях — действуй, а не уточняй.**

Принятое самостоятельно решение по продукту или интерфейсу записывай
в `docs/04-decisions.md` с пометкой `[C]` — чтобы оно не всплывало заново.

## graphify — граф проекта, обязательный вход в код

В `graphify-out/` лежит граф всего проекта: узлы, связи, «god nodes» и
сообщества. Он собран локальным AST-разбором, обновляется сам после коммитов,
слияний и переключений веток и стоит в **строгом режиме**
(`graphify install --project --strict`): первое чтение исходника в сессии
блокируется хуком, пока не выполнен хотя бы один запрос к графу.

**Правило жёсткое: связи в коде смотреть через граф, а не перебором файлов.**

| Задача | Команда |
| --- | --- |
| «Что с чем связано», «где это используется» | `graphify query "<вопрос>"` |
| Путь между двумя сущностями | `graphify path "<A>" "<B>"` |
| Разобраться в одном понятии и его окружении | `graphify explain "<узел>"` |
| Что сломается, если тронуть X | `graphify affected "X"` |
| Архитектурные узлы-хабы | `graphify god-nodes` |
| Общая картина, обзор архитектуры | `graphify-out/GRAPH_REPORT.md` |

`grep` и чтение файлов — **после** графа: чтобы посмотреть конкретные строки,
которые он указал, или чтобы их править. Не вместо него.

После изменения кода: `graphify update .` (только AST, без вызовов модели
и без ключей). Отдельно вручную это нужно редко — граф обновляют git-хуки
`post-commit`, `post-merge` и `post-checkout`.

Строгий режим временно снимается переменной `GRAPHIFY_HOOK_STRICT=0` —
только когда графа заведомо нет, например на пустом клоне до первой сборки.
